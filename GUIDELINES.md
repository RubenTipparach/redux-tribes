# Project guidelines

Adopted from `RubenTipparach/adventure-2dcon-26`'s `CLAUDE.md` and adapted to this
project. That repo's rules were written against an N64 target; the rules kept here are
the ones that hold regardless of platform. Where the original is stricter for hardware
reasons (TMEM budgets, the eleven-actor limit, libdragon toolchain specifics), it stays
in that repo — go read it there before touching anything N64-shaped.

---

## 1. No em dashes or en dashes, anywhere

Straight ASCII hyphens only, in code, comments, docs, commit messages, PR bodies and
chat. The original repo bans U+2014 and U+2013 by codepoint and greps for them before
every commit. Same rule here.

```sh
# NULL delimited on both sides: paths in this project contain spaces.
LC_ALL=C.UTF-8 git ls-files -z | xargs -0 grep -lP '[\x{2013}\x{2014}]'
```

## 2. Large features need a mockup, approved first

**Show a mockup and get it approved before implementing any large feature.** Building a
system, finding it wrong and rebuilding it costs far more than the mockup would have.

Needs a mockup:

- a new screen, HUD, panel or overlay layout
- a new game mechanic's numbers and feel (movement models, weapon pacing, boarding)
- a new ship or station model, or a resize of one
- a scenario or encounter layout
- a restructure of anything already approved

Does not: retitling a label, fixing a margin, recolouring a state, adding a button to a
row that already exists. Make the change and say what you picked.

### 2.1 A mockup is a rendered page, not a description

- **One self contained HTML file per mockup**, at `mockups/<slug>/index.html`.
- **No network at all.** No CDN script tags, no external stylesheets, no remote fonts,
  no fetch. The artifact CSP blocks them and a silently unloaded library reads as a
  broken mockup rather than a blocked request. Vendor and inline anything you need.
- **Take the numbers from the real project.** Read them out of `prototype/sim/data.js`
  and the design docs so the mockup answers the question the game will actually ask. A
  mockup at the wrong scale has answered a question nobody asked. `mockups/ship-movement`
  is the worked example: its thrust defaults are derived from the shipped
  `maxThrusterRangeValue = 40` so its envelope is directly comparable to the original's.
- **Show every state that matters,** not just the happy path: reachable and unreachable,
  at rest and at speed, first turn and mid-chain.

### 2.2 Asking for approval means LINKING the thing to be approved

Never ask "is this approved?" without a link or an image in the same message. Approval is
a judgement about how something looks or plays, and nobody can make it from a description.

- **Link the published artifact.** A repo path is not something that can be opened.
- **Or attach screenshots** when the thing is a still.
- **Say what specifically is being decided,** and what happens either way.
- **A number is not evidence for a visual decision.** Measured values belong in the
  message and none of them substitutes for the picture.

Built and unapproved is a normal state. Built, unapproved and unshown is not.

### 2.3 The mockups and the game are one description, kept in step

- Change the game, update the page in the same commit. A page describing a mechanic that
  no longer exists is worse than no page, because it is still believed.
- Change the page, carry it into the game. An approved mockup is a decision; leaving it
  unimplemented turns the mockup set into a wish list nobody can tell from the spec.
- **Prefer a check over a promise.** Where a page states a number the code holds, read it
  out of the source rather than typing it.

## 3. Every asset is a static file with an editable source

- **Static, not procedural at runtime.** Ship meshes, textures and audio are files.
- **The editable source is committed too:** the `.blend` beside the `.glb`, the
  `.aseprite` beside the `.png`, the MIDI beside the render. The archive's lost
  `Sounds/` folder and its `millitrary.blend1` with no primary file are exactly the
  failure this rule prevents.
- **Generated assets are generated by a committed script**, never by hand once.
- **Never overwrite art a person made.** Add a variant.
- **The build product must never drift from its source.** Regenerate, do not patch.
- **Model docs are regenerated whenever a model changes**, with extents measured out of
  the file rather than estimated.

## 4. Art and audio come from real tools, driven headlessly

- **3D: Blender, headless, via Python.** `blender -b file.blend --python export.py`.
- **Pixel art: Aseprite.** The archive's UI and city sets already are; keep the sources.
- **Music: MIDI is the deliverable.**
- **No cube people.** Character models get real silhouettes.
- **Every texture dimension is a power of two.**
- **No two parts share a UV area on one texture.**

## 5. Reuse, SOLID, and no divergent code paths

### 5.1 Divergent paths for like functionality are a defect

If two places need the same behaviour, they call the same code. No copies, no near
copies, no "this one is slightly different so I forked it". When a second caller needs a
variation, parameterize the one implementation.

Before writing anything new, search for the thing that already does most of the job and
extend it. If you genuinely cannot find a fit, say so before building.

Each of these exists exactly once, and every caller goes through it:

- **Turn resolution.** One `resolveTurn`. The client, the headless runner, the server and
  the replay viewer all call it.
- **Movement.** One trajectory solver. The planner's preview and the sim's execution are
  the same function, which is what makes preview equal execution.
- **Damage.** One pipeline: hit volume to subsystem split to hull. Beams, projectiles,
  missiles and rams all enter it.
- **RNG.** One seeded, stream split service. Nothing calls a global random.
- **State.** One snapshot type. Saves, replays and the multiplayer sync unit are it.

The original Unity project is the cautionary tale: two UI generations, two save writers,
two campaign layers and four weapon FX classes that were one class in a trench coat.

### 5.2 SOLID

Single responsibility, open/closed (extend by adding data or a type, not by growing a
switch), Liskov, interface segregation, dependency inversion. Practical consequence: no
globals shared between systems. Data flows through the object that owns it.

### 5.3 Data belongs in data files

Tuning values, ship stats, weapon definitions and scenario contents live in committed,
human readable, diffable files, never inline in gameplay code. `prototype/sim/data.js`
is that file today; `content/*.ron` is where it goes in the Rust port.

## 6. Levels are designed, not random

Scenarios are authored and committed as data. Procedural generation is for backdrops and
flavour, never for the encounter the player is asked to solve.

## 7. Budget everything

The web build is the constraint that bites here rather than cartridge space: wasm size,
first load time, and a single main thread. Assume a Raspberry Pi 5 class GPU as the
floor (`docs/ARCHITECTURE.md` ADR-13) and keep a quality ladder rather than one
setting.

## 8. Running it and testing it

- `node prototype/cli.js` must pass before a push.
- Determinism is checked, not assumed: `prototype/tools/xclient-check.js` resolves the
  same orders in two runtimes and compares state hashes.
- A web session can verify that something renders, that inputs route, and that numbers
  agree. It cannot verify that something feels right. Feel gets a human and a link.
